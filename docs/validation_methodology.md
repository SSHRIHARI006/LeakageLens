# Validation methodology

## Purpose

The validation harness checks whether each detector fires on the mechanism it is
supposed to detect, stays quiet on matched clean families, and produces stable
outcomes across independent seeds. It does not establish that the tool detects
all real-world leakage.

## Synthetic families

Each family is generated by `validation/generators/__init__.py` with a separated
manifest. The manifest records the family, seed, task, target, inference scenario,
train/test positional indices, expected detector outcomes, and expected counts
where a count is well defined. The manifest is evaluator metadata; it is never
passed to a detector or model.

| Family | Intended condition |
| --- | --- |
| SYN-00 | Clean classification baseline (negative control). |
| SYN-01 | Exact duplicate rows shared between train and test. |
| SYN-02 | Entity/group values present in both partitions. |
| SYN-03 | Future-dated rows used for training when temporal inference is declared. |
| SYN-04 | Post-outcome target copy exposed as a feature. |
| SYN-05 | Legitimate strong predictor (name-warning negative control). |
| SYN-06 | Rows equal after two-decimal rounding (near-duplicate positive). |
| SYN-07 | Continuous rows that must not be rounded-equal (near-duplicate negative). |
| SYN-08 | Mixed dtypes, constant, and all-null columns (negative control). |
| SYN-09 | Clean regression (negative control). |
| SYN-10 | Multiclass target (negative control). |
| SYN-11 | String binary labels (negative control for metric encoding). |
| SYN-12 | Identical features with conflicting labels. |
| SYN-13 | Unique entities with no group overlap (negative control). |
| SYN-14 | Chronological split without future contamination (negative control). |
| SYN-15 | Date column present under IID inference (negative control). |
| SYN-16 | Invalid inputs; exercised by unit/integration tests, not the benchmark. |

## Metrics

For each detector key the harness counts true positives, false positives, true
negatives, and false negatives against the manifest expectation. It reports
precision, recall, specificity, F1, false-positive and false-negative rates, and
mean detector runtime. When a family declares an expected affected-row count, the
harness also reports exact count accuracy; counts are compared exactly, not with
a tolerance.

Per-detector multi-seed statistics use the per-seed accuracy distribution. The
reported 95% interval uses a normal approximation over seeds. It is a descriptive
stability interval, not a calibrated probability, and with few seeds it should be
read as a range rather than an inferential guarantee.

## Inflation experiments

For selected families the harness runs the full audit and records the original
and safer evaluation metrics and their direction-aware difference. When the safer
protocol evaluates a different row population, the difference is labelled as an
observed protocol difference, not causal leakage inflation. `comparison_metadata`
records whether the test-row fingerprint was fixed.

## Honest reporting

- Families are project-authored; a high detection rate is not independent evidence.
- A skipped family or an omitted metric is not a pass.
- Benchmark summaries include caveats in `summary.json`; the generated report in
  `docs/validation_results.md` is produced from a specific run directory and must
  be regenerated rather than hand-edited.
- Thresholds and the risk score were not tuned on these results.

## Executed benchmark evidence

The final run used 10 seeds (`42`–`51`) across the synthetic families, producing
960 detector records, per-seed manifests, runtime measurements, and inflation
comparisons. Raw output is in `validation/results/run_20261113T102231Z/`; the
generated summary is [`validation_results.md`](validation_results.md).

The run records commit SHA, dataset hashes, Python/dependency versions, seeds,
detector configuration, and split configuration. These are descriptive project
results, not an independent generalization estimate.
